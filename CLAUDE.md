# Shadowy — рабочие принципы проекта

B2B-платформа, которая делает видимым «невидимый труд» (`neredzamais darbs`):
помощь коллегам, ввод новичков, координацию, общение с клиентом. Multi-tenant,
Next.js 14 (App Router) + Prisma + Postgres.

## Продуктовые принципы (обязательны)

### 1. Никакого ранжирования людей
Любая метрика по человеку показывается **для поддержки и распределения
нагрузки**, а не для оценки или соревнования.

- **Нельзя:** медали, подиумы, лейдерборды, «лучший/худший сотрудник»,
  соревновательные цвета (зелёный «молодец» / красный «плохо») на персонах.
- **Можно:** нейтральная активность и выделение «у кого много/мало» как сигнал
  для перераспределения работы; взаимопомощь (кто кому помогает); часы как
  описание, а не цель.

**Почему:** ядро позиционирования — «Shadowy nav novērošanas rīks» (это не
слежка). Соревнование по людям превращает «честную видимость нагрузки» в табло
надзора и ломает доверие сотрудников, а доверие — это и есть воронка внедрения.

Практика: диаграмма помощи, матрица «Darbinieku klienti», список активности —
формулируются как поддержка/нагрузка; дельты периодов — нейтральным цветом.

### 2. Язык интерфейса — только латышский
Весь пользовательский текст (заголовки, кнопки, подписи, пустые состояния,
ошибки, подсказки) — на латышском. Код и имена переменных — на английском.

## Инженерные принципы

### Multi-tenant изоляция — критично
Каждый запрос к БД содержит `organizationId` из сессии. Роль-скоуп применяется
**последним**, после пользовательских фильтров, чтобы crafted-URL не мог
расширить видимость. Для записей используйте `entryScopeForSession(session)` из
`src/lib/entry-filter.ts` и спредите его ПОСЛЕ `buildEntryWhere(sp)`.

Эта инвариант покрыта тестами — `src/lib/entry-filter.test.ts`. При изменении
скоупинга/фильтров запускайте `npm test` и дополняйте тесты.

### Базы данных: dev ≠ prod
Локальный `DATABASE_URL` **никогда** не должен указывать на прод/пилотную БД.
Используйте отдельную ветку Neon или локальный Postgres. `npm run db:push`
проходит через `scripts/db-guard.ts`; задайте `PROTECTED_DB_HOST` в окружении,
чтобы он блокировал случайную запись в прод.

### Выкладка: прод используют живые клиенты
Каждый push в `main` Vercel сразу выкладывает в прод, а им каждый день
пользуется пилотный клиент.

- **Перед push в `main`:** `npm run typecheck && npm test`.
- **GitHub Actions** (`.github/workflows/ci.yml`) на каждый push в
  `main`/`preview` и на каждый PR гоняет typecheck, lint, тесты и сборку.
  Красный прогон — сначала чинить, поверх не строить.
- **Общие части** (записи, клиенты, сессии, категории, расчёт часов) меняются
  только вместе с тестами. Расчёт часов по клиентам и лимитов покрыт
  `src/lib/client-matrix.test.ts`.
- **Схема БД — только добавлять:** новые таблицы и nullable-поля. Не
  переименовывать и не удалять колонки в той же выкладке, где код перестаёт их
  использовать. Изменение схемы применять к **каждой** прод-базе *до* мерджа
  кода, который на него опирается (сейчас прод-база одна; когда появится
  вторая — к обеим).
- **Откат:** Vercel → Deployments → предыдущая выкладка → Instant Rollback.

## Полезные команды
- `npm run dev` — запуск
- `npm run typecheck` — проверка типов
- `npm test` — тесты (Vitest)
- `npm run db:push` — схема в БД (через предохранитель)
